# 跨境电商运营日报/周报自动化工具

这是一个用于生成跨境电商运营日报和周报的自动化项目。

项目通过 Python、FastAPI、Streamlit、Docker 和 n8n，完成从数据读取、指标计算、风险识别、报告生成、Gmail 发送到失败告警的完整流程。

当前版本主要用于项目演示和流程验证，默认使用演示数据或本地数据文件，不包含任何公司真实数据、账号密码或 API 密钥。

## 一、项目功能

### 1. 数据读取与处理

- 读取销售、广告和库存数据
- 支持演示数据和本地数据文件
- 支持销售额、订单量、销量、广告花费、广告销售额等字段
- 对数据进行基础清洗和格式转换
- 为后续接入真实电商平台 API 预留数据接口

### 2. 经营指标计算

- 计算 GMV
- 计算订单量
- 计算销量
- 计算广告花费
- 计算广告销售额
- 计算 ROAS
- 计算预计利润
- 计算利润率
- 统计库存风险
- 支持日报和周报不同统计周期

### 3. 日报和周报生成

- 自动生成跨境电商经营日报
- 自动生成跨境电商经营周报
- 日报统计单日经营情况
- 周报统计过去 7 天经营情况
- 周报将当前 7 天数据与上周同期 7 天数据进行对比
- 输出经营结论、关键指标和异常信息
- 输出销售、广告和库存方面的运营建议
- 报告内容支持 Markdown 格式

### 4. 异常识别

- 识别销售额下降
- 识别广告投入产出比偏低
- 识别广告花费异常
- 识别库存不足风险
- 根据数据变化生成风险提示
- 支持在报告中输出需要关注的经营问题

### 5. Streamlit 数据看板

- 提供可视化数据看板
- 展示销售、广告和库存数据
- 展示核心经营指标
- 展示异常风险
- 支持在网页中查看报告
- 支持下载 Markdown 格式报告
- 方便后续扩展图表、筛选和历史报告功能

### 6. FastAPI 报告接口

- 提供报告生成 API
- 提供服务健康检查 API
- 支持通过 HTTP 请求生成日报
- 支持通过 HTTP 请求生成周报
- 方便 n8n 或其他系统调用
- 后续可以被 Coze、Dify、企业内部系统或前端页面调用

### 7. n8n 自动化工作流

- 每天早上 08:00 自动触发日报任务
- 每周一早上 08:10 自动触发周报任务
- 自动调用报告生成接口
- 自动接收生成后的报告内容
- 自动调用 Gmail 发送报告
- 自动处理发送失败情况
- 支持后续连接企业微信、飞书、钉钉等系统

### 8. Gmail 报告发送

- 日报正常发送到指定 Gmail 邮箱
- 周报正常发送到指定 Gmail 邮箱
- 邮件标题自动带上报告日期
- 邮件正文使用自动生成的日报或周报内容
- Gmail 是日报和周报的正常发送渠道

### 9. 发送失败自动重试

- 当报告生成或 Gmail 发送失败时，自动进行重试
- 最多自动重试 3 次
- 用于处理临时网络异常、接口短暂不可用和邮件服务响应失败等问题
- 通过重试机制提高自动化任务的稳定性

### 10. PushPlus 失败告警

- PushPlus 不负责正常发送日报和周报
- PushPlus 只负责发送任务失败通知
- 当任务连续重试 3 次仍然失败时，触发 PushPlus 告警
- 将失败信息推送到个人微信
- 方便及时发现日报或周报没有正常发送
- 后续可以替换为企业微信群、飞书群、钉钉群或其他告警渠道

### 11. 服务健康检查

- 提供报告 API 健康检查
- 检查报告服务是否正常运行
- Docker 启动时等待报告 API 健康后再启动相关服务
- 降低服务刚启动时接口不可用导致任务失败的风险
- 方便后续接入日志、监控和告警系统

## 二、项目整体流程

销售、广告、库存数据

↓

Python 数据读取、清洗和指标计算

↓

FastAPI 生成日报或周报

↓

n8n 定时触发自动化任务

↓

Gmail 正常发送日报或周报

↓

如果发送失败，自动重试 3 次

↓

3 次仍然失败时

↓

PushPlus 推送失败通知到个人微信

## 三、日报流程

每天早上 08:00：

1. n8n 自动触发日报工作流
2. 调用 `POST /generate-report`
3. 传入日报参数
4. Python 读取并处理数据
5. 计算当天经营指标
6. 识别销售、广告和库存异常
7. 生成日报内容
8. 通过 Gmail 发送日报
9. 如果发送失败，自动重试最多 3 次
10. 3 次仍失败时，通过 PushPlus 推送失败告警

## 四、周报流程

每周一早上 08:10：

1. n8n 自动触发周报工作流
2. 调用 `POST /generate-report`
3. 传入周报参数
4. Python 获取最近 7 天数据
5. 计算过去 7 天的经营指标
6. 与上周同期数据进行对比
7. 识别销售、广告和库存异常
8. 生成周报内容
9. 通过 Gmail 发送周报
10. 如果发送失败，自动重试最多 3 次
11. 3 次仍失败时，通过 PushPlus 推送失败告警

## 六、当前版本的数据说明

当前项目默认使用演示数据或本地数据文件验证流程。

当前版本的情况：

- 当前报告中的销售、广告和库存数据不代表真实公司数据
- 当前版本没有接入任何公司的真实业务 API
- `api.py` 是项目自己搭建的内部报告 API
- n8n 调用的是本项目的 `report-api`
- Gmail 用于正常发送日报和周报
- PushPlus 只用于发送最终失败告警
- 项目中不包含公司真实业务数据
- 项目中不包含真实账号、密码或 API 密钥

当前版本重点验证以下自动化闭环：

数据读取 → 指标计算 → 风险识别 → 报告生成 → Gmail 发送 → 失败重试 → 微信告警

因此，本项目目前定位为：

一个已经完成核心自动化闭环、可继续接入真实业务 API 的跨境电商运营报告自动化 MVP。

## 七、本地运行方式

### 1. 创建虚拟环境

python -m venv .venv

### 2. 激活虚拟环境

.\.venv\Scripts\Activate.ps1

### 3. 安装 Python 依赖

python -m pip install -r requirements.txt

### 4. 启动 Streamlit 数据看板

streamlit run app.py

启动后访问：

http://localhost:8501

## 八、Docker 运行方式

安装 Docker Desktop 后，在项目根目录执行：

docker compose up --build

启动后可以访问：

- 数据看板：http://localhost:8501
- 报告 API：http://localhost:8000/docs
- n8n：http://localhost:5678

停止服务：

docker compose down

修改 Python 代码后重新构建：

docker compose up --build

## 九、FastAPI 接口

### 1. 健康检查接口

请求方式：

GET /health

作用：

- 检查报告 API 是否正常运行
- 供 Docker 健康检查使用
- 方便 n8n 或其他系统判断服务状态

### 2. 生成报告接口

请求方式：

POST /generate-report

日报请求示例：

{
  "period": "日报",
  "source": "sample"
}

周报请求示例：

{
  "period": "周报",
  "source": "sample"
}

当接口返回状态码 `200` 时，说明报告生成成功。

## 十一、PushPlus 失败告警说明

当前推送逻辑：

- Gmail：正常发送日报和周报
- PushPlus：只发送最终失败通知
- 重试次数：最多 3 次
- 告警对象：个人微信

PushPlus 失败通知可以包含：

- 日报或周报任务名称
- 执行时间
- 失败节点
- 错误原因
- 重试次数
- 建议排查方向

PushPlus Token 不应直接写入公开代码。

可以使用环境变量：

PUSHPLUS_TOKEN=你的 PushPlus Token

不要将真实 Token 提交到 GitHub。

## 十二、以后改成企业通知渠道

当前使用 PushPlus 将失败通知推送到个人微信，适合个人使用和项目演示。

以后公司正式使用时，可以将失败通知改成：

- 企业微信群机器人
- 飞书群机器人
- 钉钉机器人
- Slack
- Microsoft Teams
- 企业内部消息系统
- 短信或电话告警系统

替换时，只需要修改 n8n 中的失败通知节点，正常的 Gmail 报告发送流程不需要改变。

整体逻辑保持不变：

正常成功 → Gmail 发送日报或周报

发送失败 → 自动重试 3 次

最终失败 → 企业通知渠道发送告警

## 十三、以后接入真实公司 API 时需要做什么

### 第一步：确认真实数据来源

需要确认公司实际使用的系统，例如：

- 电商平台 API
- ERP 系统
- 广告平台 API
- 订单系统
- 库存系统
- 数据仓库
- 公司内部数据库

### 第二步：确认真实数据字段

需要确认可以获取以下字段：

- 日期
- 店铺
- SKU
- 销售额
- 订单量
- 销量
- 广告花费
- 广告销售额
- 库存
- 在途库存
- 日均销量
- 采购周期
- 退款金额
- 商品成本

### 第三步：新增真实数据连接层

建议新增独立的数据连接目录：

connectors/

├─ sales_api.py

├─ ads_api.py

└─ inventory_api.py

推荐结构：

真实业务 API → 数据连接层 → 统一字段格式 → 报告计算逻辑 → 日报和周报

不要把真实 API 请求代码全部直接写进报告计算逻辑中。

### 第四步：配置 API 密钥

不要把密钥直接写进 Python 文件、README 或 n8n 工作流。

可以使用：

- `API_BASE_URL`
- `API_KEY`
- `API_SECRET`
- `DATABASE_URL`
- `PUSHPLUS_TOKEN`

本地使用 `.env` 文件时，必须将 `.env` 加入 `.gitignore`，不能上传到 GitHub。

### 第五步：统一字段格式

真实 API 返回的字段可能和当前项目不同，需要在数据连接层完成字段映射。

例如：

真实平台字段：`total_amount`

项目统一字段：`sales`

真实平台字段：`order_count`

项目统一字段：`orders`

### 第六步：替换演示数据

修改：

`platform_data.py`

或者新增真实数据连接器，让系统从真实 API 获取数据。

报告计算逻辑尽量保持不变，这样可以降低改造成本。

### 第七步：检查数据口径

接入真实数据后，需要重点检查：

- 日报统计的是哪一天
- 周报统计的是哪一周
- GMV 是否包含退款
- 广告花费是否含税
- ROAS 的分子和分母是什么
- 利润是否扣除商品成本
- 库存是否包含在途库存
- 时区是否为北京时间
- API 失败时是否触发重试
- Gmail 发送失败是否自动重试 3 次
- 重试是否可能造成重复发送
- 最终失败是否能够通过 PushPlus 告警

### 第八步：配置正式运行环境

正式使用前，需要确认：

- n8n 服务长期运行
- Docker 容器设置自动重启
- 报告 API 有健康检查
- 工作流有失败重试
- 工作流有最终失败告警
- Gmail 凭据已经配置
- PushPlus Token 已安全保存
- 收件人地址正确
- 服务器时区正确
- 不会因为重复执行造成重复发信
- 日志和执行记录可以正常查看
